# Governance

## Classification scheme

Every column of every dbt model carries `meta: {pii, classification, owner}`
in `schema.yml`. A generic dbt test (`governance_meta`) and a CI check
(`validate_meta_completeness`) fail on any untagged column — governance is
enforced, not documented.

| classification | meaning | examples |
| --- | --- | --- |
| `public` | Safe to surface anywhere | `status`, `channel`, `revenue`, `country` |
| `internal` | Business identifiers and raw timestamps | `customer_id`, `order_id`, `sku`, `created_ts` |
| `restricted` | Confidential; requires special access | PII (`full_name`, `email`, `phone`, `body_text`) |

`pii: true` marks personal data specifically; every `pii: true` column must
also be `restricted`. The single source of truth for PII discovery is
`governance.pii.get_pii_columns(manifest)` — the agent guardrails and the
grant generator both read from it.

## Role matrix

Generated by `governance/grants.py` from the meta tags and reapplied by the
dbt `on-run-end` hook on every build:

| role | scope | mechanism |
| --- | --- | --- |
| `analyst_ro` | Marts minus restricted columns | generated secure views (`analyst_ro.<model>`) — Snowflake `CREATE SECURE VIEW` + `GRANT SELECT`; DuckDB restricted-stripped views |
| `engineer_rw` | All marts tables | `GRANT SELECT ON ALL TABLES IN SCHEMA <marts>` |
| `pii_reader` | Marts including restricted columns | explicit per-table `GRANT SELECT` |

DuckDB has no role-based access control; the closest equivalent is the
`analyst_ro` view schema, and `engineer_rw`/`pii_reader` remain informational.

## Guardrail list (agent)

Every tool invocation passes through `agent/guardrails.py`; no tool is
callable without the wrapper.

| rule | default | behaviour on breach |
| --- | --- | --- |
| PII denial (args) | all `pii: true` columns | `GuardrailViolation` naming column + classification; tool denied |
| PII denial (results) | same set | re-scan of returned records; unexpected PII column aborts the call before the LLM sees it |
| Row cap | hard `LIMIT 1000` injected | larger requested limits are clamped |
| Result byte ceiling | 256 KiB | returned records are truncated to fit |
| Cost cap | 64 MiB estimated bytes/question | run aborts with a partial answer + reason |
| Wall-clock timeout | 120 s/question | run aborts with a partial answer + reason |
| Tool-call rate limit | 25 calls/question | run aborts (fatal) |
| Question rate limit | 60 questions/minute | question rejected with an explanatory answer |
| Read-only SQL | sqlglot parse | compiled SQL must be exactly one `SELECT`; separators, DDL, DML (including inside CTEs) are rejected |

## Audit and replay

- `meta.agent_audit`: one row per tool call — args, compiled SQL, rows,
  bytes scanned, duration, guardrail verdict, caller role, LLM model,
  manifest hash. Written for allowed *and* denied calls.
- `meta.agent_questions`: one row per question — final (or partial) answer,
  status, total cost. Written even when the question fails.
- `meta.manifest_registry`: one row per manifest snapshot (hash, git sha,
  dbt version, model count). `transform_and_govern` snapshots every build to
  `artifacts/manifests/<hash>.json`.
- `awo replay --question-id X` re-executes the recorded tool calls against
  the pinned manifest and reports `IDENTICAL`, `DRIFTED` (changed rows), or
  `STALE_SCHEMA` (pinned model gone).
